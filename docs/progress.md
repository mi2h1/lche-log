## 検討事項・将来の課題

> 2026-08-29 時点。実施は未定。

### 画像ストレージ（Supabase Storage）
本番の実測値（2026-08-29 時点、公開サイトの anon key で参照）:

| 項目 | 実測 |
|---|---|
| 画像枚数 | 83枚（vs_records 83件と一致、孤立ファイルなし） |
| 合計サイズ | 149.7 MB / 1GB（使用率 15%） |
| 平均サイズ | 1.80 MB（中央値 1.91MB、最大 4.39MB、1MB超が60%） |
| 投稿ペース | 全期間 月6.6枚 / 直近6か月 月4.8枚 |
| 増加量 | 月あたり 約12〜14 MB |

**1GB到達は 2031年後半〜2032年頃**（残り874MB ÷ 月14MB ≒ 61か月）。
容量を理由に移行する必要は当面ないと判断し、**現状維持**とした。

画像は原寸のままアップロードしている（`js/vs-record.js`）。
「原寸で保持したい」という方針のため、アップロード前のリサイズは行わない。

### 先に効くのは容量ではなく転送量（egress）
Supabase 無料プランの egress は月5GB。画像が平均1.8MBのため:

| 閲覧のされ方 | 1訪問あたり | 月5GBに達する訪問数 |
|---|---|---|
| トップを開くだけ（10件） | 約18MB | 約280回 |
| 最後までスクロール（83件） | 約150MB | 約34回 |

無限スクロール導入前は1訪問で必ず約150MB流れていたため、この点は改善済み。
**判断材料は Supabase ダッシュボードの Usage → Egress の実消費量**。未確認。

### 検討したが見送った案
- **Cloudinary への移行** — 原寸をそのまま保存し、配信時のみURLパラメータ
  (`w_800,f_auto,q_auto`) で縮小する方式。無料枠は保存10GB・帯域20GB・変換2万回。
  静的サイトから unsigned upload preset で直接アップロード可能。
  「原寸保持」と両立するため、**egress が月5GBの半分を超えたら再検討する**。
  既存の `image_url` は絶対URLのため、新規投稿だけ切り替えれば既存画像は壊れない。
  注意: unsigned upload はプリセット名が公開JSに出るため第三者もアップロード可能
  （現状の anon key + 全許可RLSと同種の露出）。
- **Supabase の画像変換機能** — Pro プラン以上の機能で無料プランでは使えない。
- **X（Twitter）の画像URLを流用** — Xは再エンコード・4096px縮小・EXIF除去を行うため
  原寸が保持されない。ポスト削除やCDN仕様変更で画像が壊れるリスクもあり不採用。
- **VPS への移行** — 空きディスク17GB（Supabaseの17倍）で画像問題が根本的に解消し、
  サーバ側認証により `users` テーブルの課題も直せる。ただし容量が5年持つと分かったため
  見送り。実施する場合の段階手順:
  1. nginx / Caddy で静的配信 + Let's Encrypt（ドメイン要）
  2. `deploy.yml` を GitHub Pages publish から VPS への rsync に変更
  3. 画像を VPS ディスクへ（新規分のみ切り替え）
  4. アップロード用APIを立て、認証をサーバ側に移す
  5. （将来）Postgres も VPS へ → Supabase スリープ問題と keepalive 自体が不要になる

### 画像のバックアップ（未実施）
バケットが公開設定のため、**anon key だけで一覧取得・一括ダウンロードが可能**。
ダッシュボードに一括ダウンロード機能はないためスクリプトで行う。
- 一覧: `POST /storage/v1/object/list/vs-images`（`prefix: "vs-records/"`）
- 取得: 各オブジェクトの公開URLを取得

現状、画像の実体は Supabase 上にしか存在しない。keepalive が停止するとプロジェクトが
スリープする構造のため（過去2回停止実績あり）、定期バックアップの実施を検討したい。
83枚の一括ダウンロードは約150MB = 月間 egress の約3%を消費する点に注意。

### その他の残課題
- `users` テーブルの RLS 未設定により `password_hash` が公開読み取り可能になり得る。
  Supabase ダッシュボードでの実設定確認が必要。恒久対応は Supabase Auth 等への移行。
- keepalive の60日自動停止対策（自動コミット）は最終コミットから50日経過時に発火。
  2026-08-29 のコミットにより、次回判定は 2026-10-18 頃。未発火のため要観察。

### 2026-08-29 — トップページを10件ずつの無限スクロールに変更

**問題**
トップページが公開済みの posts と vs_records を毎回すべて取得していたため、
投稿が増えるほど初期表示が重くなる構造だった。

**対応**
`js/blog.js` を 10件ずつ読み込む無限スクロールに変更（`PAGE_SIZE` で件数変更可）。
- 2テーブルを統合したタイムラインのため offset は使えず、`created_at` を基準にした
  キーセットページネーションを採用。posts / vs_records からそれぞれ取得してマージし、
  先頭 PAGE_SIZE 件だけを表示、最後に表示した投稿の created_at を次回の基準にする。
- 同時刻の投稿を取りこぼさないよう `lte` で取得し、重複は ID の Set で除外。
  除外される分（基準時刻と同時刻の表示済み件数 `boundaryCount`）だけ多めに取得して
  常に10件表示されるようにした。
- users / categories は件数が少ないため初回のみ取得してキャッシュ。
- IntersectionObserver で下端を検知。非対応ブラウザは scroll イベントにフォールバック。
  1ページで画面が埋まらない場合は `maybeLoadMore()` が続けて読み込む。
- 読み込み失敗時は再読み込みボタンを表示（自動再取得は停止）。
- `index.html` に読み込み表示・終端メッセージ・トリガー要素を追加。
  `.main-content` が `display: flex` のままだと横並びになるため `flex-direction: column` を追加。
- VS記録の画像に `loading="lazy"` を追加。

**確認**
Supabase クエリと DOM をスタブしたスクリプトで11パターンを検証。
投稿なし / 3件 / ちょうど10件 / 20件 / 30件 / VS記録のみ / 両テーブル混在 /
同時刻11件 / 同時刻25件 / 両テーブル同時刻15件ずつ、いずれも
ページ件数・重複なし・時系列順・網羅・終端メッセージが期待通りであることを確認。
検証中に「2ページ目以降が9件になる」「同時刻が10件以上あると1件表示されない」不具合を
発見し、上記の `boundaryCount` 方式で修正済み。
ブラウザでの実動作（スクロール検知・レイアウト）は未確認。

   最終コミットから50日以上経過している場合のみ `docs/keepalive-activity.txt` を更新して
   push し、リポジトリ活動を発生させ続けることで60日自動停止を回避する。
   （`permissions: contents: write` を付与）

### 2026-05-23 — keepalive ワークフロー修正

**問題**
keepalive ワークフローが 2026-05-05 以降毎日 failure し、Supabase プロジェクトがスリープしていた。

**原因**
`@supabase/supabase-js` の新バージョンが Node.js ネイティブ WebSocket を要求するようになったが、
ワークフローが Node.js 20（ネイティブ WebSocket 非対応）を使用していたためクライアント生成時にクラッシュ。

```
Error: Node.js 20 detected without native WebSocket support.
```

**対応**
`.github/workflows/keepalive.yml` の `node-version: '20'` → `'22'` に変更。
Node.js 22 以降はネイティブ WebSocket 対応済みのため解決。

**確認**
手動実行で成功を確認。
